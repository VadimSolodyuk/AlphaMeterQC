# Концепция приложения AlphaMeterQC

Статус: черновик.

## 1. Назначение и границы первой версии

### 1.1. Назначение

AlphaMeterQC предназначено для контроля наличия и проверки корректности данных о параметрах электросети в цепях учёта электроэнергии, хранящихся в базе данных ПО «АльфаЦЕНТР».

### 1.2. Границы первой версии

Первая версия охватывает автоматическое выполнение проверок службой по расписанию и работу специалиста с результатами через веб-интерфейс, включая ручной запуск проверки.

Приложение получает данные из БД ПО «АльфаЦЕНТР», определяет, какие ожидаемые данные отсутствуют на момент проверки, выполняет применимые проверки параметров электросети и сохраняет результаты в собственном хранилище. Специалист просматривает результаты последней проверки, вносит примечания к выявленным отклонениям, задаёт настройки ручной проверки и формирует отчёт.

## 3. Проблема и ожидаемая польза

Для проверки корректности параметров электросети цепей учёта электрической энергии специалист оценивает данные по каждому присоединению: наличие напряжений и токов, их соответствие допустимым значениям, согласованность фазовых углов и соответствие токов потреблению электроэнергии.

Проверка повторяется для большого числа присоединений. Она требует сопоставления нескольких групп параметров с учётом схемы подключения и характера нагрузки, поэтому трудоёмка и подвержена риску ошибки. Несколько нарушений могут возникать одновременно.

AlphaMeterQC должно выполнять проверки единообразно и показывать, какие данные не поступили, какие отклонения выявлены и какие проверки выполнить не удалось. Автоматическое выполнение проверок по расписанию не зависит от подключения специалиста к веб-интерфейсу. Результаты сохраняются в приложении и используются специалистом для анализа, внесения примечаний и формирования отчёта. Специалист использует результат для принятия решения о дальнейших действиях.

> Примечание к доработке: описать текущий порядок проверки, объём проверяемых присоединений, получателей результатов и существующие возможности АльфаЦЕНТР.

## 4. Основной сценарий

### 4.1. Запуск приложения на сервере

1. Специалист вручную запускает AlphaMeterQC на сервере ПО «АльфаЦЕНТР».
2. При запуске открывается графический диалог ввода параметров подключения к БД. Специалист использует единую учётную запись. Ранее сохранённые параметры, кроме пароля, подставляются автоматически. Пароль вводится при каждом запуске приложения.
3. После подтверждения ввода приложение получает параметры из диалога и выполняет подключение к БД.
4. Если подключение к БД не удалось, приложение сообщает причину ошибки и предоставляет возможность повторного ввода параметров подключения.
5. После успешного подключения приложение продолжает работу на сервере в качестве системной службы и становится доступным специалистам через веб-интерфейс.

> Примечание к доработке: проверить согласованность запуска службы и использования пароля со спецификацией login_dialog; описать использование пароля в течение работы службы без сохранения на диск.

### 4.2. Автоматическое выполнение проверок

1. Работающая служба автоматически запускает проверки по расписанию. Расписание по умолчанию — ежедневно в 07:30, 12:00 и 16:00 по системному времени сервера.
2. При первом запуске автоматической проверки начало окна — текущая дата минус 7 суток. Конец окна — момент запуска проверки.
3. При последующих запусках начало окна — момент запуска последней успешно завершённой автоматической проверки, но не ранее чем за 14 суток до момента запуска текущей проверки. Из двух моментов выбирается более поздний. Конец окна — момент запуска текущей проверки. Ручные проверки не изменяют границу следующей автоматической проверки.
4. Приложение получает из БД необходимые данные, выполняет применимые проверки по всем доступным измерениям окна и сохраняет результаты в собственном хранилище.
5. Автоматическая проверка выполняется без подключения специалиста к веб-интерфейсу.

> Примечание к доработке п. 2: определить точное время начальной границы первого окна и момент первой проверки после запуска службы.

> Примечание к доработке пп. 3–4: определить критерий успешного завершения проверки и поведение при пересечении запусков, ошибке проверки и возобновлении работы после остановки службы.

### 4.3. Работа специалиста с результатами

1. Специалист проверяет результаты не реже одного раза в неделю; день по умолчанию — пятница.
2. Специалист на своём автоматизированном рабочем месте (АРМ) открывает веб-интерфейс приложения и указывает ФИО.
3. Приложение отображает сохранённые результаты последней проверки.
4. Специалист анализирует результаты и вносит или изменяет примечания. Примечание сохраняется в поле «Примечание» записи соответствующего отклонения.
5. Специалист может задать настройки контроля и запустить проверку вручную. Приложение получает необходимые данные из БД, выполняет применимые проверки и сохраняет результаты.
6. Специалист формирует отчёт по результатам проверки с сохранёнными примечаниями и выгружает его в файл электронной таблицы для подписания и направления руководителю отдела.
7. Руководитель определяет мероприятия по устранению выявленных отклонений.

> Примечание к доработке п. 3: определить отображение отсутствия результатов до первой проверки и ошибок последней проверки.

> Примечание к доработке п. 6: описать состав и форму веб-отчёта, выбор результатов для отчёта и формат файла электронной таблицы.

### 4.4. Настройки контроля

Настройки контроля задаются специалистом через веб-интерфейс и применяются только к проверкам, запускаемым вручную.

Настройка «Глубина анализа, суток» принимает целые значения от 1 до 14; значение по умолчанию — 7. Начало периода ручной проверки — 00:00:00 календарной даты, предшествующей дате запуска проверки на указанное число суток. Конец периода — дата и время запуска проверки.

> Примечание к доработке: дополнить состав настроек по результатам проработки диагностических правил; для каждой настройки описать назначение, область применения, допустимые значения и значение по умолчанию. Определить сохранение настроек ручной проверки и значения остальных параметров автоматических проверок.

### 4.5. Журнал работы службы

Служба ведёт журнал работы. В журнале фиксируются запуск и остановка службы, начало и завершение проверок, границы анализируемого периода, результат выполнения и ошибки.

> Примечание к доработке: определить способ выявления и регистрации пропущенных запусков после возобновления работы службы, срок хранения журнала и способ его просмотра.

## 5. Проверки и диагностические правила

### 5.1. Период анализа и эпизоды отклонений

Приложение анализирует все доступные измерения периода, определённого для автоматической или ручной проверки, и выделяет отдельные эпизоды отклонений. Дата и время запуска проверки фиксируются один раз и используются как конец периода анализа и как момент расчёта продолжительности эпизодов без установленного окончания.

Для каждого эпизода указываются:

- Дата и время начала — время первого измерения с отклонением, если по анализируемым данным установлено его возникновение после измерения без этого отклонения. Если отклонение присутствует уже в первом доступном измерении и начало не установлено по сохранённой истории, поле остаётся пустым.
- Дата и время окончания — время первого последующего измерения, в котором условие отклонения больше не выполняется. Если окончание не установлено, поле остаётся пустым; отдельный статус незавершённого эпизода не отображается.
- Продолжительность — разность между временем окончания и установленным началом эпизода. Если начало неизвестно, отсчёт ведётся от первого доступного измерения с отклонением. Если окончание не установлено, продолжительность рассчитывается до времени запуска проверки, даже если последнее доступное измерение получено раньше. Формат — чч:мм:сс; часы отображаются суммарно, без сброса после 24 часов, например 27:15:00.

Границы эпизода определяются по измерениям и не означают точного физического времени возникновения и прекращения отклонения. При неизвестном начале рассчитанная продолжительность не означает полной длительности отклонения. Расчёт до запуска проверки сам по себе не подтверждает сохранение отклонения после последнего доступного измерения. Повторное возникновение отклонения после его прекращения учитывается как новый эпизод.

> Примечание к доработке: описать сопоставление эпизодов по сохранённой истории, использование сохранённого опорного времени при неизвестном начале, обработку пропусков измерений и расчёт продолжительности при неподтверждённой непрерывности эпизода.

### 5.2. Хранение эпизодов

Приложение сохраняет эпизоды отклонений и примечания в собственном хранилище. Незавершённые эпизоды сохраняются до установления окончания независимо от возраста.

Завершённые эпизоды вместе с примечаниями сохраняются, если дата и время окончания эпизода находятся в интервале от 00:00:00 календарной даты «текущая дата минус 14 суток» до текущего момента включительно. Используется системное время сервера.

> Примечание к доработке: описать обновление и очистку хранилища, сохранность данных при перезапуске службы и обработку ранее сохранённых эпизодов при изменении правил контроля. Срок хранения эпизодов с неизвестным окончанием после пропуска измерений описать совместно с правилами п. 5.1.

### 5.3. Проверки параметров и диагностика

- Отсутствие измерения отличается от измеренного нулевого напряжения или тока. Нулевой ток сам по себе не считается неисправностью.
- Для счётчиков прямого включения отдельные пороги наличия напряжения и тока не задаются: измеренное ненулевое значение считается наличием. Отклонение напряжения оценивается относительно номинального по общему правилу. Предложенное начальное значение допуска — ±10 %.

  > Примечание к доработке: проработать правило отклонения напряжения и применимость порога 0,05 А вторичного тока для счётчиков, включённых через трансформаторы тока.

- Симметрия токов проверяется только при наличии тока во всех трёх фазах. Для присоединений ниже и выше 1 кВ применяется одинаковый критерий: отношение наибольшего фазного тока к наименьшему превышает заданный порог. Предложенное начальное значение порога — 2. Для присоединений ниже 1 кВ проверку можно отключить в веб-интерфейсе; другие проверки при этом сохраняются.

  > Примечание к доработке: проработать критерий симметрии, правило для напряжения ровно 1 кВ и применение настройки отключения проверки с учётом п. 4.4.

- Если доступные измерения показывают отсутствие тока в части фаз при его наличии в других, симметрия не оценивается. Для присоединений выше 1 кВ фиксируется «Отсутствует ток фазы». Для присоединений ниже 1 кВ при напряжении во всех трёх фазах и токе только в одной допускается предположение «Возможно однофазная нагрузка».

  > Примечание к доработке: проработать условия применимости и исходные данные для выводов об отсутствии тока фазы и возможной однофазной нагрузке.

- Сообщения «Возможно однофазное подключение; требуется проверка» для напряжения и тока только в одной фазе и «Ток без напряжения» для тока при измеренном нулевом напряжении той же фазы остаются предложениями.

  > Примечание к доработке: проработать условия формирования этих диагностических сообщений.

Допуски и пороги ручной проверки задаются в веб-интерфейсе; их применённые значения указываются в отчёте. Отключённая проверка отмечается как «не выполнялась по настройке», а не как отсутствие отклонений. Предложенные начальные значения не являются нормативным заключением.

> Примечание к доработке: для каждого правила описать применимость, необходимые данные, условия срабатывания, результат и ограничения диагностики. Описать проверки фазовых углов и соответствия токов потреблению электроэнергии. Проверить доступность исходных данных в Oracle. Значения параметров автоматических проверок описать в п. 4.4.

### 5.4. Записи об отклонениях и примечания

Каждое отклонение оформляется отдельной записью. Базовые признаки записи — присоединение и вид отклонения; номер счётчика указывается справочно.

> Примечание к доработке: определить полный ключ записи с учётом фазы и нескольких эпизодов одного вида отклонения на одном присоединении, а также связь эпизодов с записями отчёта.

Примечание сохраняется при выходе из поля ввода в поле «Примечание» записи соответствующего отклонения. При повторном формировании отчёта используется сохранённое примечание.

На время редактирования блокируется только эта запись, а не всё присоединение или отчёт. Другие записи можно редактировать одновременно.

> Примечание к доработке: определить таймаут снятия блокировки при прерванной сессии и взаимодействие автоматического обновления результатов с редактированием примечаний.

> Примечание к доработке: описать сохранение связи с примечанием при повторных проверках, изменении границ эпизода и повторном возникновении отклонения после перерыва.
