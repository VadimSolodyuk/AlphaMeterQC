## 1. Название продукта / фичи
Модуль `ext_alphaSrv` — служба динамической оптимизации параметров опроса точек учёта (ТУ).

## 2. Цель создания
Автоматизировать корректировку интервалов и количества попыток опроса ТУ в БД АльфаЦЕНТР в зависимости от актуальности данных и качества связи, исключив ручной труд инженеров.

**Бизнес-показатели успеха:**
- Сокращение ручных операций инженеров по настройке опроса.
- Оптимизация расхода трафика за счёт снижения количества попыток опроса при стабильной связи.
- Обеспечение актуальности данных в АльфаЦЕНТР без превышения тарифных лимитов операторов.

## 3. Стейкхолдеры
| Стейкхолдер | Роль | Ключевые интересы и потребности |
|-------------|------|--------------------------------|
| Инженеры по сопровождению АСКУЭ | Пользователи / Операторы | Исключение рутинных корректировок параметров, прозрачность работы службы |
| Руководитель направления | Внутренний заказчик | Снижение затрат на связь, стабильность сбора данных, соответствие SLA |
| Администраторы серверов | Эксплуатация | Простое управление службой (старт/стоп), минимальные привилегии, логирование |
| Команда разработки AlphaMeterQC | Интеграторы (Этап 2) | Чёткий API/интерфейс для управления параметрами из UI |

## 4. Целевая аудитория
- **Основные пользователи:** Инженеры и системные администраторы, работающие с сервером АльфаЦЕНТР.
- **Контекст:** Сервер расположен в ЦОД/на объекте, обслуживает территориально удалённые ТУ. Связь по GSM нестабильна.
- **Сценарий:** Служба работает фоновой службой ОС. Инженер контролирует логи, при необходимости останавливает службу или корректирует параметры через UI (Этап 2).

## 5. Проблемы и потребности
| Проблема | Описание | Как решает модуль |
|----------|----------|-------------------|
| Ухудшение GSM-сигнала | Обрывы связи во время опроса приводят к потере данных | Автоматическое переключение на режим с увеличенным интервалом и количеством попыток |
| Ручная корректировка параметров | Трудозатраты инженеров, риск ошибок и превышения лимитов на связь | Динамическое управление интервалом (1ч/6ч) и попытками (10/5) на основе времени последних данных |
| Необходимость применения настроек | Изменения в БД не применяются без перезапуска сервиса | Автоматический перезапуск `AlphaSrv` после внесения изменений в БД |

## 6. Ключевые характеристики

### 6.1. Функциональные возможности
- Конфигурация в JSON:
  `{"db": {"ip": str, "port": int, "username": str, "password": str}, "usp_ids": 1000, "time_window_start": "02:00", "time_window_end": "02:00", "interval_opt": 1, "interval_econ": 6, "retries_opt": 10, "retries_econ": 5, "check_start": 4}`.
  Параметры (`usp_ids`,`time_window_start`, `time_window_end`, `interval_opt`, `interval_econ`, `retries_opt`, `retries_econ`, `check_start`) необязательны; при отсутствии любого из них служба использует значения по умолчанию (указанные выше) и логирует предупреждение.
  Для каждой константы выполняется проверка:
    - `usp_ids` — целое положительное число (если указан в JSON).
    - `time_window_start`, `time_window_end` — формат HH:MM, 00:00–23:59.
    - `interval_opt`, `interval_econ` — целое положительное число (часы), не более 24.
    - `retries_opt`, `retries_econ` — целое положительное число, не более 20.
    - `check_start` — целое число 0–23.
  При отсутствии ключа, несоответствии формата или выходе за допустимый диапазон параметр игнорируется, используется значение по умолчанию, в лог записывается WARNING с указанием имени параметра, переданного и ожидаемого значения.
- Запуск и управление в качестве службы ОС.
- Планировщик: проверка условия 1 раз в час, начиная с часа, указанного в параметре `check_start` (по умолчанию 04:00) ежедневно. По результату устанавливается интервал опроса ТУ: 1 ч (режим оптимизации) или 6 ч (режим экономии).
- Логика анализа данных по каждой ТУ:
  - Если `time_window_start` == `time_window_end`:
    - Если `last_data` относится к предыдущему дню (любое время) → режим оптимизации: интервал 1 ч, попытки 10.
    - Иначе → режим экономии: интервал 6 ч, попытки 5.
  - Иначе (границы различны):
    - Если `time_window_start` предыдущего дня <= `last_data` < `time_window_end` текущего дня → режим оптимизации.
    - Иначе → режим экономии.
- Если `last_data` отсутствует (NULL) для ТУ, считать данные устаревшими и применять режим экономии (интервал 6 ч, попытки 5).
- Применение изменений: обновление конфигурации ТУ в БД АльфаЦЕНТР + автоматический перезапуск `AlphaSrv`.
- Обработка ошибок:
  - При неудачном перезапуске `AlphaSrv` — повторная попытка через 1 мин, до 3 раз. При исчерпании — логирование ошибки, продолжение работы без изменений параметров.
  - При некорректном формате JSON, отсутствии обязательных ключей "db" или отсутствии значения `usp_ids` в таблице БД — логирование ошибки, остановка службы.
- Логирование всех действий, изменений параметров, статусов перезапусков, а также событий запуска и остановки службы.
- Ограничения по управлению службой и перезапуску AlphaSrv описаны в разделе 9.

### 6.2. Нефункциональные требования
- Язык реализации: Python 3.9+ (или аналогичный, совместимый с инфраструктурой сервера).
- Зависимости: Только драйвер БД АльфаЦЕНТР, доступ к Service Manager ОС.
- Безопасность: Запуск от выделенного пользователя с минимальными правами. На этапе 1 параметры подключения хранятся в JSON-файле с ограничением доступа через ACL ОС.
- Надёжность: Атомарность транзакций БД, обработка сбоев сети/БД без падения службы, graceful shutdown.
- Производительность: Минимальное потребление CPU/RAM, отсутствие блокировок основных процессов АльфаЦЕНТР.

## 7. Уникальные преимущества (USP)
- **Полная автоматизация:** Исключение ручного вмешательства в настройку опроса ТУ.
- **Адаптивность:** Динамическое переключение режимов в зависимости от актуальности данных и качества связи.
- **Простота внедрения:** Этап 1 реализуется как автономная служба без изменения ядра AlphaSrv.

## 8. Этапы реализации
| Этап | Описание |
|------|----------|
| 1 | Разработка автономной службы Windows. Конфигурация — из JSON-файла (формат описан в п.6.1). Реализация логики анализа временного окна, обновления БД и перезапуска `AlphaSrv`. Логирование всех событий. Управление только через конфигурационный файл и логи (UI не предусмотрен). |
| 2 | Интеграция с UI AlphaMeterQC: запуск/остановка службы, выбор УСПД, настройка интервала опроса, количества попыток и временного окна. Параметры подключения к БД — из `login_dialog` передаются при запуске AlphaMeterQC. |

**Acceptance Criteria для Этапа 1:**
- AC-1 (п.6.1, п.9): Служба корректно устанавливается и запускается как служба ОС.
- AC-2 (п.6.1): `AlphaSrv` перезапускается в течение 2 минут после окончания обновления параметров опроса в БД.
- AC-3 (п.6.1): При некорректном формате JSON, отсутствии обязательных ключей "db" или отсутствии номера из `usp_ids` в таблице БД служба останавливается, ошибка логируется.
- AC-4 (п.6.1): При отсутствии ключа необязательной константы в JSON, несоответствии формата или выходе за допустимый диапазон параметр игнорируется, используется значение по умолчанию (указанное в спецификации), в лог записывается WARNING с указанием имени параметра, переданного и ожидаемого значения.
- AC-5 (п.6.1): При сбое перезапуска `AlphaSrv` служба не падает, ошибка логируется, дальнейшая работа продолжается.
- AC-6 (п.6.1, п.10.3): Все ключевые события (старт, стоп, обновление БД, перезапуск, ошибки) фиксируются в логе с временными метками.
- AC-7: Служба выполняет проверку условий ровно 1 раз в час, начиная с часа `check_start`, и не чаще.
- AC-8: Для ТУ с `last_data` в пределах временного окна устанавливается интервал 1 ч и 10 попыток; вне окна — 6 ч и 5 попыток. При отсутствии `last_data` (NULL) применяется режим экономии.
- AC-9: При равенстве `time_window_start` и `time_window_end` режим оптимизации применяется, если `last_data` относится к предыдущему дню (любое время).

## 9. Предположения и ограничения
- **Перезапуск** AlphaSrv выполняется через команду ОС (например, sc stop/start на Windows, systemctl на Linux в перспективе). После отправки команды остановки служба ext_alphaSrv должна ожидать статус «stopped» (с таймаутом не более 30 секунд), затем отправить команду запуска и ожидать статус «running» (таймаут 30 секунд). Если статус не достигнут за отведённое время, попытка считается неудачной.
- **Служба не должна блокировать** работу основного `AlphaSrv` или других компонентов АльфаЦЕНТР.

## 10. Мониторинг и алертинг

### 10.1. Метрики (Этап 2)
Служба должна предоставлять возможность сбора следующих метрик (через структурированное логирование или простой файл-счётчик):
- Количество успешных/неуспешных перезапусков `AlphaSrv`.
- Количество изменённых ТУ (суммарно за сессию).
- Текущий режим (оптимизация/экономия) и время последнего переключения.
- Время последнего успешного обновления конфигурации в БД.

### 10.2. Алертинг (Этап 2)
Архитектура логов должна позволять:
- Экспорт метрик в формате, совместимом с Prometheus (через sidecar-экспортер или HTTP-эндпоинт).
- Отправку критических ошибок (например, невозможность перезапустить `AlphaSrv` после 3 попыток) в систему оповещения (e-mail, Telegram, SNMP trap).

### 10.3. Требования к логированию
Логи должны быть структурированными (формат JSON) и содержать:
- Временную метку (ISO 8601), уровень (INFO, WARN, ERROR), идентификатор УСПД.
- Для каждого изменения параметров опроса – количество затронутых ТУ и новый режим.
- Для каждого перезапуска `AlphaSrv` – статус (успех/неуспех) и количество попыток.
- Для каждого пропущенного или некорректного параметра конфигурации – имя параметра, переданное и ожидаемое значение.
Пример структуры JSON-лога:
```json
{
  "timestamp": "2026-08-01T14:30:00.000Z",
  "level": "INFO",
  "usp_id": 1000,
  "message": "Режим изменён на оптимизацию",
  "details": {
    "affected_tu_count": 45,
    "new_interval": 1,
    "new_retries": 10
  }
}
Все логи (включая WARNING при необязательных параметрах) должны соответствовать этому формату.

| ЦОД | Центр обработки данных |
| ACL | Access Control List (список контроля доступа) |
| UI | User Interface (пользовательский интерфейс) |
| API | Application Programming Interface (программный интерфейс) |
