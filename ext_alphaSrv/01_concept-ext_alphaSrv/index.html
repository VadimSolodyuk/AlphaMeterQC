КОНЦЕПЦИЯ ПРОДУКТА / ФИЧИ

Версия: 1.0 Дата: 01-08-2026 Автор: В.Л. Солодюк Проект: ПО «AlphaMeterQC» / Модуль ext_alphaSrv Статус: Черновик

1. Название продукта / фичи

Модуль ext_alphaSrv — служба динамической оптимизации параметров опроса точек учёта (ТУ).

2. Цель создания

Автоматизировать корректировку параметров опроса счетчиков (ТУ) и УСПД в БД АльфаЦЕНТР в зависимости от актуальности данных, исключив ручной труд инженеров.

Бизнес-показатели успеха:

  • Сокращение ручных операций инженеров по настройке опроса
  • Оптимизация расхода трафика за счёт снижения количества попыток опроса при стабильной связи
  • Обеспечение актуальности данных в АльфаЦЕНТР без превышения тарифных лимитов операторов

4. Целевая аудитория

  • Основные пользователи: Инженеры и системные администраторы, работающие с сервером АльфаЦЕНТР.
  • Контекст: Сервер расположен в ЦОД/на объекте, обслуживает территориально удалённые ТУ. Связь по GSM нестабильна.
  • Сценарий: Служба работает фоновой службой ОС. Инженер контролирует логи, при необходимости останавливает службу или корректирует параметры через UI (Этап 2).

6. Ключевые характеристики

6.1. Функциональные возможности

  • Конфигурация в JSON: {"db": {"ip": str, "port": int, "username": str, "password": str}, "interval": 60, "interval_amr": 8, "connection_retries": 5}, где:

  • interval: интервал запуска процессов анализа и коррекции данных в минутах (ext_alphaSrv).

  • interval_amr: устанавливает значение в plan_opr2.interv
  • connection_retries: устанавливает значение в place2.kol_pop

    Если указан в JSON - выполняется проверка :

  • usp_ids — целое положительное число.
  • star_thour, end_hour, hour_check_start — целое число 0–23 (час).
  • interval_opt, interval_econ — целое положительное число (часы), не более 24.
  • retries_opt, retries_econ — целое положительное число, не более 20. Ключ db, в котором указываются параметры подключения к БД, и все ключи внутри него — обязательны, а все остальные — необязательны и при отсутствии любого из них служба использует значения по умолчанию (указанные выше в JSON).
  • Путь к конфигурационному файлу по умолчанию:
  • Windows: C:\ProgramData\AlphaMeterQC\ext_alphaSrv\config.json
  • Linux: /etc/alphameterqc/ext_alphaSrv/config.json Путь может быть переопределён через аргумент командной строки --config или переменную окружения EXT_ALPHASRV_CONFIG.
  • Запуск и управление в качестве службы ОС.
  • Планировщик: проверка условия 1 раз в час. Проверка не выполняется в интервале [00:00, hour_check_start). По результату устанавливается интервал опроса ТУ: interval_opt (режим оптимизации) или , interval_econ (режим экономии).
  • Логика анализа данных по каждой ТУ:
  • Если last_data != (NULL | ""):
    • Если (вчерашняя дата + star_thour) <= last_data < (сегодняшняя дата + end_hour) → режим оптимизации: интервал interval_opt, попытки retries_opt.
  • Иначе → режим экономии: интервал interval_econ, попытки retries_econ. last_data - время последних данных в БД.
  • Применение изменений пакетное (1 раз/цикл) после анализа всех ТУ:
  • обновление конфигурации ТУ в БД АльфаЦЕНТР только в случае изменения интервала или попыток,
  • автоматический перезапуск AlphaSrv только в случае необходимости обновления конфигурации ТУ в БД АльфаЦЕНТР.
  • Обработка ошибок:
  • Если при запуске службы ext_alphaSrv не удаётся установить соединение с БД или в процессе работы происходит разрыв соединения с БД (неверные параметры, недоступность сервера), служба выполняет 3 попытки подключения с интервалом 30 секунд. После исчерпания попыток служба логирует ошибку с указанием причины и завершает работу (код 1).
  • При неудачном перезапуске AlphaSrv — повторная попытка через 1 мин, до 3 раз. При исчерпании — логирование ошибки, продолжение работы без изменений параметров.
  • При некорректном формате JSON, отсутствии обязательных ключей — логирование ошибки, остановка службы.
  • При отсутствии в БД номера УСПД из usp_ids — логирование ошибки, остановка службы
  • При несоответствии формата или выходе за допустимый диапазон необязательного параметра - используется значение по умолчанию, в лог записывается WARNING с указанием имени параметра, переданного и ожидаемого значения.
  • Логирование всех действий, изменений параметров, статусов перезапусков, а также событий запуска и остановки службы.
  • Ограничения по управлению службой и перезапуску AlphaSrv описаны в разделе 9.

6.2. Нефункциональные требования

  • Язык реализации: Python 3.9+ (или аналогичный, совместимый с инфраструктурой сервера).
  • Зависимости: Только драйвер БД АльфаЦЕНТР, доступ к Service Manager ОС.
  • Безопасность: Запуск от выделенного пользователя с минимальными правами. На этапе 1 параметры подключения хранятся в JSON-файле с ограничением доступа через ACL ОС.
  • Надёжность: Атомарность транзакций БД, обработка сбоев сети/БД без падения службы, graceful shutdown.
  • Производительность: Минимальное потребление CPU/RAM, отсутствие блокировок основных процессов АльфаЦЕНТР.

7. Уникальные преимущества (USP)

  • Полная автоматизация: Исключение ручного вмешательства в настройку опроса ТУ.
  • Адаптивность: Динамическое переключение режимов в зависимости от актуальности данных и качества связи.
  • Простота внедрения: Этап 1 реализуется как автономная служба без изменения ядра AlphaSrv.

8. Этапы реализации

Этап Описание
1 Разработка автономной службы Windows. Конфигурация — из JSON-файла (формат описан в п.6.1). Реализация логики анализа временного окна, обновления БД и перезапуска AlphaSrv. Логирование всех событий. Управление только через конфигурационный файл и логи (UI не предусмотрен).
2 Интеграция с UI AlphaMeterQC: запуск/остановка службы, выбор УСПД, настройка интервала опроса, количества попыток и временного окна. Параметры подключения к БД — из login_dialog передаются при запуске AlphaMeterQC. Требуется дополнительная спецификация API/UI и метрик (п.10.1–10.2).

Acceptance Criteria для Этапа 1:

  • AC-1 (п.6.1, п.9): Служба корректно устанавливается и запускается как служба ОС.
  • AC-2 (п.6.1): AlphaSrv перезапускается в течение 2 минут после окончания обновления параметров опроса в БД.
  • AC-3 (п.6.1): При некорректном формате JSON, отсутствии обязательных ключей или отсутствии в БД номера УСПД из usp_idsслужба останавливается, ошибка логируется.
  • AC-4 (п.6.1): При несоответствии формата или выходе за допустимый диапазон необязательного параметра - используется значение по умолчанию, в лог записывается WARNING с указанием имени параметра, переданного и ожидаемого значения.
  • AC-5 (п.6.1): При сбое перезапуска AlphaSrv служба не падает, ошибка логируется, дальнейшая работа продолжается.
  • AC-6 (п.6.1, п.10.3): Все ключевые события (старт, стоп, обновление БД, перезапуск, ошибки) фиксируются в логе с временными метками.
  • AC-7 (п.6.1): Служба выполняет проверку условий ровно 1 раз в час, кроме интервала 00:00 - hour_check_start.
  • AC-8 (п.6.1): Для ТУ с last_data в пределах временного окна устанавливается интервал interval_opt и retries_opt попыток; вне окна и при last_data != (NULL | "") — интервал interval_econ и retries_econ попыток.
  • AC-9 (п.9): При остановке службы через sc stop (или аналог) все соединения с БД закрываются, незавершённые транзакции откатываются, процесс завершается. В логе фиксируется событие остановки.
  • AC-10 (п.6.1): При недоступности БД на старте или в процессе работы служба ext_alphaSrv делает 3 попытки подключения с интервалом 30 секунд, после чего останавливается с ошибкой в логе.
  • AC-11 (п.10.3): Логи должны ротироваться по дням. Хранится не более 7 файлов. Старые логи архивируются или удаляются автоматически.

9. Предположения и ограничения

  • Служба ext_alphaSrv выполняет перезапуск AlphaSrv с помощью команд ОС:
  • Windows: Остановка: sc stop AlphaSrv Запуск: sc start AlphaSrv Проверка статуса: sc query AlphaSrv (парсинг строки STATE; ожидаемые значения: 1 STOPPED, 4 RUNNING).
  • Linux (перспектива): Остановка: systemctl stop AlphaSrv Запуск: systemctl start AlphaSrv Проверка статуса: systemctl is-active AlphaSrv (возвращает active или inactive). Таймауты:
    • Ожидание статуса «stopped» — не более 30 секунд.
    • Ожидание статуса «running» — не более 30 секунд. Если статус не достигнут за отведённое время, попытка считается неудачной. Для проверки статуса AlphaSrv используется команда ОС, возвращающая строку состояния. Парсинг выполняется по ключевым словам (например, STOPPED/RUNNING для Windows, active/inactive для Linux). Если команда не возвращает ожидаемый формат, попытка считается неудачной.
  • Корректное завершение службы ext_alphaSrv: При получении сигнала остановки ОС (SIGTERM, Ctrl+C, sc stop) служба обязана:
  • Закрыть все соединения с БД (выполнить rollback незавершённых транзакций, если они есть).
  • Если текущая проверка не завершилась, она прерывается принудительно, соединения закрываются.
  • Завершить процесс с кодом 0.
  • Служба не должна блокировать работу основного AlphaSrv или других компонентов АльфаЦЕНТР.

10. Мониторинг и алертинг

10.1. Метрики (Этап 2)

Служба должна предоставлять возможность сбора следующих метрик (через структурированное логирование или простой файл-счётчик):

  • Количество успешных/неуспешных перезапусков AlphaSrv
  • Количество изменённых ТУ (суммарно за сессию)
  • Текущий режим (оптимизация/экономия) и время последнего переключения
  • Время последнего успешного обновления конфигурации в БД

10.2. Алертинг (Этап 2)

Архитектура логов должна позволять:

  • Экспорт метрик в формате, совместимом с Prometheus (через sidecar-экспортер или HTTP-эндпоинт).
  • Отправку критических ошибок (например, невозможность перезапустить AlphaSrv после 3 попыток) в систему оповещения (e-mail, Telegram, SNMP trap).

10.3. Требования к логированию

Логи должны быть структурированными (формат JSON) и содержать:

  • Временную метку (ISO 8601), уровень (INFO, WARN, ERROR), идентификатор УСПД.
  • Для каждого изменения параметров опроса – количество затронутых ТУ и новый режим.
  • Для каждого перезапуска AlphaSrv – статус (успех/неуспех) и количество попыток.
  • Для каждого пропущенного или некорректного параметра конфигурации – имя параметра, переданное и ожидаемое значение.
  • Пример структуры JSON-лога:

```json { "timestamp": "2026-08-01T14:30:00.000Z", "level": "INFO", "usp_id": 1000, "message": "Режим изменён на оптимизацию", "details": { "affected_tu_count": 45, "new_interval": 1, "new_retries": 10 } } Все логи (включая WARNING при необязательных параметрах) должны соответствовать этому формату. - Логи должны ротироваться по времени (ежедневно). Максимальное количество хранимых файлов — 7 (настраиваемое значение). Имена файлов логов: ext_alphaSrv_YYYY-MM-DD.log. Старые логи архивируются или удаляются автоматически.
